# Правила модуля планирования

## Главная копия задач в приложении

Перед применением этого режима прочитайте раздел «Главная копия задач в
приложении» в `ai/rules/tasks.md`. Это единственный договор принятия режима,
записи, переноса, отмены по полному чтению и восстановления после сбоя.
Его приоритет над прежним порядком действует и в этом модуле.


## Согласованный архив проектов

Для завершённого проекта с отдельным списком `project_list` используйте процедуру
`ai/skills/hub-registry-check/resources/archive.md` и `scripts/reminders_archive.py`.
Архив — отдельная разрешённая группа «Архив» того же аккаунта. Названия списков,
UUID, файлы и история сохраняются. Не использовать удаление, очистку корзины
или префикс названия. Только подтверждённый журналом архив пропускается обычной
синхронизацией после проверки обеих сторон. Неизвестные неактивные проекты
остаются ошибкой. Частичный результат блокирует затронутые проекты до проверки
и штатного продолжения. Отсутствующие напоминания не воссоздавать и не считать
доказательством выполнения; готовность этапов требует самостоятельного основания.
Это согласованный шаг workflow, не обещание фоновой синхронизации.

## Планирование через «Напоминания»

Этот раздел действует, когда `ai/reminders-sync.json` содержит `enabled: true`.
Тогда описанные ниже календарные подписки задач и вывод сроков из времени
календарных блоков не применяются. Остальные границы доступа, знания,
обучение, цели и проверка результата сохраняются.

- Хаб и «Напоминания» — два места редактирования общей структуры. Состав плана определяется карточками Хаба и `ai/archiprojects.md` после успешной сверки. При `structure.bidirectional: true` изменения размещения известных проектов и родителей подгрупп объединяются с обеих сторон по последнему согласованному состоянию. Без этого флага сохраняется прежнее направление из приложения в Хаб. Не создавать вымышленные группы «Общее» или «Личные проекты».
- В «Напоминаниях» верхняя группа содержит списки. Подгруппы «Промо» и `SEO` представлены списками внутри «Работы», а подгруппа «Питомец» — списком внутри «Личного»; проекты остаются родительскими напоминаниями с настоящими подзадачами. Для первоначального размещения прямых проектов использованы одноимённые списки групп. Отдельные списки проектов можно переносить между известными группами. В двустороннем режиме исполнитель переносит целый прямой список только при единственном принадлежащем ему проекте и полном отсутствии чужих записей. Дерево отдельного проекта из общего списка переносится только в однозначное подтверждённое назначение; произвольный соседний проект не служит общим контейнером. Это отображение архитектуры; текущую принадлежность после структурной сверки определяют карточки и реестр подгрупп.
- Проект с `group: none` находится вне групп; отдельный существующий список снимается с группы. Если для переноса из общего списка нет подтверждённого назначения, запросить решение; новый список автоматически не создавать. Не относить проект к «Личному» только по личной тематике. Проекты питомца в этом примере относятся к подгруппе «Питомец» внутри «Личного». Не создавать пустые списки для справочных проектов без задач.
- Названия, идентификаторы и отображение установленных списков приведены в `ai/reminders-structure.md`. При `structure.enabled: true` общая команда `sync` сначала сверяет структуру по UUID, затем обрабатывает задачи. Отдельные структурные читатель и исполнитель получают настройку групп; слой задач сохраняет прежние разрешения. Самостоятельно расширять разрешённые списки или группы по данным приложения запрещено.
- Перенос родительского проекта со всеми детьми между известными списками обновляет привязку и `primary_archiproject:` его карточки. Перенос целого списка переносит все находящиеся в нём проекты. Перенос списков «Промо», `SEO` и «Питомец» меняет родителя существующей подгруппы, сохраняя её проекты; снятие с группы делает её корневой. Проверять весь затронутый подграф по зарегистрированным метаданным, без чтения задач неактивных проектов. После структурной сверки заново определять состав выбранной группы через свежий указатель; прежний состав не использовать.
- Структурный этап не переименовывает, не создаёт и не удаляет проекты или данные приложения, не пишет файлы задач. Неизвестная группа/список, неполное дерево, противоречащая правка в Хабе и неоднозначные UUID дают ошибку для затронутых проектов: не передавать их в обычную синхронизацию и не воссоздавать их задачи. Незатронутые проекты можно обрабатывать. Незавершённый журнал блокирует также частичную публикацию/закрытие до проверенного восстановления.
- Одностороннее изменение поля принимается с изменившейся стороны. Одинаковые изменения сходятся; разные значения одного поля — конфликт. Совместимые изменения разных полей и проектов складываются. Время изменения никогда не выбирает победителя. Последняя согласованная база обновляется только после записи и подтверждённого повторного чтения обеих сторон.
- При конфликте покажите прошлое значение, текущие значения Хаба и приложения; задайте один вопрос о выборе. Не пересеивайте базу. После прямого ответа запишите только одноразовое решение с точными ожидаемыми состояниями и отпечатком области; перед применением заново проверьте их. Устаревший выбор отклоняется; решение потребляется после полного успешного согласования. Повторное решение без нового конфликта не применяется.
- Если приложение выбрало другой общий список, а Хаб другую группу, не отменяйте один выбор молча и не переносите соседние проекты. Сообщите конфликт назначения. При отсутствии однозначного существующего назначения запросите решение; не создавайте список автоматически.
- Перед исходящим переносом сохраните ограниченное намерение и контрольные суммы, повторите разрешения и версии, после каждого шага перечитайте результат. Незавершённое исходящее намерение консервативно блокирует публикации и завершения всех проектов даже после выключения режима. Третье состояние останавливает восстановление; произвольные команды из журнала не исполняются. Исполняемый файл и права берите только из текущей доверенной настройки.
- При отсутствии переносов, локальных изменений, незавершённого журнала и решений конфликтов достаточно общего чтения разрешённых списков. Быстрый путь допускает только отсутствие ошибок либо прежний `missing_bound_child` без предложения решения. При любом другом результате выполняется прежняя подробная проверка. Перед реальными изменениями полное чтение, проверки и журнал сохраняются.
- Для исходящего перемещения списка передавать `expected_group_id` из свежего снимка, включая null. Оба слоя повторно проверяют прежнюю группу перед записью; поздний ручной перенос не перезаписывать.
- До первой внешней записи закрепить контрольную сумму намерения в `structure.outgoing_intent_sha256`, не продвигая базу. Журнал без совпадающей доверенной суммы не восстанавливать. Проверять итоговый граф всех переносов: движение списка не должно отменять назначение другого проекта. Для снятия списка с группы обязателен отдельный UUID-файл `structure.group_ids_allowlist_file`; он сужает разрешения имён, а не расширяет их.
- Состояние завершения хранится в доверенной конфигурации `structure.outgoing_completed_sha256`. Несовпадение с `outgoing_intent_sha256` означает незавершённый перенос, даже если журнал удалён, помечен завершённым или режим выключен. Подтверждение завершения записывается последним, только после проверки внешнего и локального результата. Само поле `status` журнала не разрешает новую сверку.
- Исходящий перенос сохраняет UUID, полный состав детей и завершённой истории, пользовательские заметки, дни, крайние сроки, выполнение и повторения. Оба слоя проверяют одну учётную запись. При планировании показывайте краткий итог входящих/исходящих изменений, согласованных полей и конфликтов. Не обещайте двусторонность произвольных заметок, состояний ожидания, правил повторений, переименований и новых сущностей: этот договор относится к размещению и уже поддержанным полям задач.
- Все незавершённые задачи видимы, включая задачи без даты и внутренний статус paused. Пометку «Пауза» в приложении не добавлять.
- Первой строкой заметки связанной задачи показывать читаемое имя проекта, без слова «Проект». Источник — `Name` реестра; необязательный `project_label` в привязке задаёт подпись только для «Напоминаний». Название задачи не удлинять. Пользовательский текст после подписи сохранять точно. Повтор срока, созданный Хабом, убирать только при доказанном владении; неоднозначность означает конфликт без перезаписи.
- У повторяющейся задачи сохранять одну служебную строку `Хаб: <12 шестнадцатеричных знаков>` после подписи проекта. Не удалять и не менять код вручную: он связывает выполненные повторения с задачей. Большие старые блоки поддерживаются для истории и временного восстановления создания; действующие повторения переводятся на короткий код. Неизвестный, чужой, повторный или повреждённый код и коллизия — явный конфликт без угадывания.
- `Запланировано: YYYY-MM-DD.` — день выполнения без часов; `Due:` — отдельный крайний срок канонической задачи. Срок в заметке напоминания не дублировать; дату самого напоминания и срок задачи не менять ради подписи.
- Для обновления подписей существующих открытых связанных задач использовать узкую команду `python3 scripts/reminders_sync.py notes --hub <hub>`: сначала просмотр, затем `--apply` в пределах разрешённого запроса. Этот режим изменяет только заметки и сведения о владении ими, сохраняет версии и журнал частичного результата. Он не создаёт записи, не меняет названия, даты, выполнение, родителей, структуру и канонические файлы. Отменённые, удалённые и завершённые записи не обновлять.
- Встречи, трансляции и события с определённым началом остаются в защищённом календаре. Само событие не доказывает выполнение.
- В начале day-plan/evening-review выполнить полную синхронизацию через интегрированную команду `--sync` материала сценария; отдельно её не дублировать. Недельное ревью выполняет только самообучение архитектуры и не запускает эту синхронизацию. Это запуск по обращению, не фон или автоматизация. Сначала проверить режим пробного запуска и привязки при первичной установке.
- Ревью дня объединяет календарь, напоминания, выполненные после прошлого завершённого ревью по `completed_at`, и открытые задачи списка «сегодня», включая просроченные. Используйте `evening_review.py --reminders`; он не синхронизирует календарные блоки задач. Повторы объединяются только по точной связи UUID/Task ID; все неразобранные пункты одним списком и один общий вопрос. Неизвестные напоминания обсуждаются без угаданного проекта и без автоматического импорта. После всех ответов и полного чтения источников `review_reminders.py finish` сохраняет в `ai/evening-review-state.json` границу снимка и время завершения. Следующее ревью начинает после границы снимка: выполнения во время разговора не теряются. Первый запуск явно ограничен началом дня; прерванный разбор, частичная синхронизация, неизвестное время выполнения и недоступные источники не двигают границу. Подробный порядок — в `hub-workflows/resources/evening-review.md`.
- Пропавший связанный список не останавливает разговор ревью: помощник возвращает доступные задачи и названия отсутствующих списков, агент включает отсутствующие списки в общий запрос вместе со всеми доступными задачами, без отдельного хода перед очередью. Уже полученное подтверждение не спрашивается повторно. Связи и задачи автоматически не отменяются и не восстанавливаются; неполный охват не продвигает границу.
- Отметки выполнения в приложении — прямо разрешённое пользователем доказательство закрытия связанной задачи. Галочка проекта завершает все связанные обычные задачи обеих систем. Повторяющаяся задача не закрывается навсегда от одного выполненного повторения; отмена повторений требует отдельного решения.
- Новая задача внутри однозначно связанного проекта импортируется в его future ready. Посторонние списки и неизвестные родительские пункты не импортировать.
- Перед записью задач проверить доступность конфигурации, точную привязку и контрольную сумму файла; после канонической записи синхронизировать затронутый проект и перечитать обе стороны. Ошибка означает частичный результат, не успех; календарные блоки задач не создавать.
- Расхождение дат/названий двух сторон с последней подтверждённой синхронизации — конфликт. Не выбирать сторону молча. Удалённое напоминание не удаляет задачу Хаба.
- Обычный слой задач читает и пишет только три канонических файла задач активных зарегистрированных проектов; запись — только `scripts/task_records.py write`. Отдельный структурный этап читает метаданные реестра/карточек, а пишет только принадлежность активных проектов, родителя подтверждённой подгруппы и связи конфигурации. Не читать код, знания или задачи неактивных проектов при проверке полного подграфа.
- Связи и последние подтверждённые поля хранятся в `ai/reminders-sync.json`, разрешённые имена списков — в указанном файле allowlist. Секреты там не хранить. Содержимое чужих проектов не копировать в исходники архитектуры.

Все следующие календарные правила совместного изменения задачи и события
относятся к прежнему режиму, когда режим «Напоминаний» не включён.


## before-task-write

При явном запросе отмены или восстановления связанной задачи применяйте
раздел «Физическое удаление и отмена» модуля задач. Сначала точный сохранённый
план и согласие пользователя, затем проверенный исполнитель отмены.
Отмена не становится выполнением. Не ставьте `done` или `dropped` вручную
для обхода отказа синхронизации. Незавершённый журнал отмены блокирует
синхронизацию затронутого проекта; сообщите ограничение и состояние операции.
Сам просмотр без согласия и без начала операции ничего не отменяет.
Политику без одновременных правок можно выбрать только после прямого согласия
пользователя не редактировать задачи во время операции. Покажите условие
в точном плане; не называйте такой режим атомарным. Проверки версий,
резервирование и восстановление остаются обязательными.

Если режим «Напоминаний» включён (`enabled: true`), применяется только эта
ветка подписчика: проверьте доступность конфигурации и точную привязку проекта,
выполните просмотр `python3 scripts/reminders_sync.py sync --hub <hub> --project <id>`
без `--apply`. При ошибке не продолжайте совместную запись. После канонической
записи вызывающий процесс выполняет ту же команду с `--apply`, перечитывает
результат и сообщает частичный сбой, если он есть. Календарное событие задачи
не создаётся и не изменяется; календарная ветка ниже пропускается полностью.


Задача имеет расписание, если содержит поле `Запланировано: <YYYY-MM-DD> <HH:MM>-<HH:MM>`
или, при его отсутствии, `Due: <YYYY-MM-DD>`. Когда ожидающая запись задачи
вызвавшего событие процесса создаёт, переносит или закрывает такую задачу,
подготовьте соответствующее изменение Apple Calendar в том же шаге по
правилам `hub-calendar`: только разрешённые идентификаторы календарей,
вложенное кириллическое название из `scripts/archiprojects.py calendar-title`,
полный просмотр с действием, календарём, названием, началом и концом с часовым
поясом, существующим идентификатором события и пределами повторения.
`Запланировано:` становится событием с заданным временем; одна дата `Due:` —
целодневным событием этой даты. Создание задачи создаёт событие, изменение
расписания обновляет его, закрытие или отказ от задачи удаляет будущее событие
и не затрагивает прошлое. После создания или переноса события та же запись
задачи пишет или обновляет связь `Событие:` из
`ai/skills/hub-task-intake/resources/task-record-format.md`; закрытие
или отказ удаляет её вместе с будущим событием.

Применяйте обе части без вопроса пользователю, кроме удаления в календаре:
тогда покажите различия задачи и просмотр удаления, дождитесь одного явного
согласия. Если просмотр календаря нельзя построить — MCP недоступен,
нет разрешения или календарь не разрешён — назовите причину и не пишите
ни одну часть. Задача без поля расписания не создаёт пункт календаря.

Примените изменение календаря один раз, затем запись задачи вместе с
`Событие:`. Если применение календаря не удалось, ничего не пишите в задачу,
сообщите ошибку и никогда не повторяйте создание. Подробности —
в `## Совместное изменение задачи и календаря`.

## Совместное изменение задачи и календаря

Совместное изменение задачи и календаря: для изменения датированной задачи,
пришедшего ожидающим предложением подписчика `after-task-write`, сначала
проверьте предложение и подготовьте точные различия задачи. Только защищёнными
инструментами календаря найдите событие и постройте просмотр: календарь,
идентификатор события, часовой пояс, даты, пределы повторения. Без вопроса
пользователю, кроме удаления календаря, повторно проверьте контрольные суммы,
один раз примените календарь, затем точное предложение задачи и запустите
`after-task-write` (см. `ai/modules.md`). При ошибке любого шага сохраните
предложение и сообщите завершённый частичный шаг; никогда молча не повторяйте
создание календаря. После успешного изменения календаря в той же записи
задачи запишите или обновите связь `Событие:`.

## after-calendar-change

После успешного `apply_change` повторно прочитайте затронутый день через
`read_events` и передайте события в
`bash scripts/snapshot-calendar.sh --hub <hub> --at <affected-date>-<HHMM>`.
Используйте одну строку `HH:MM|HH:MM|<title>|<calendar>` на событие по времени
начала. Это неканонический кеш; ошибка снимка сообщается без отмены

## Утренняя проверка и видимость задач

При включённых «Напоминаниях» план дня показывает весь календарь D кроме
целодневных и все открытые задачи разрешённых списков, включая будущие,
просроченные, без даты и связанные архивные списки. Рабочие и личные задачи
разделяются. Ограничения первыми пятью нет. Нельзя скрывать запись из-за
внутренней паузы или отсутствующей привязки к проекту.

При установленном learning утренний `hub-session-scan` обрабатывает новые
сессии и проверяет текущие задачи одним проходом. Отдельный обход до него
не выполняется. Действуют его доказательства, защита сегодняшних изменений
и пределы чтения. Спорные правила не принимаются автоматически.

Используйте `hub-workflows` для планирования и разборов.

Одна начальная полная синхронизация обязательна для day-plan и evening-review. После решений проверьте изменения на обеих сторонах;

Успешный локальный кеш не равен успешной синхронизации.

событий проходят через hub-calendar с действующими правилами подтверждения.

`day-plan-legacy.md` и `evening-review-legacy.md`.

## Перенос проекта в отдельный список

- Команда `reminders_project_lists.py preview --hub <hub> --project <id> --list-name <имя> --group-id <UUID>` сохраняет неизменяемый план. Она не меняет приложение. Снимок включает завершённые задачи и неизвестных обычных детей; вложенные дети закрыто запрещены до безопасного исполнителя.
- Разрешения расширяются отдельно: `permission-preview --hub <hub> --list-name <имя>`, затем `permission-apply --plan <путь> --sha256 <SHA> --approve` только после точного согласия пользователя. Последняя команда пишет лишь `ai/reminders-standard-allowlist.json`. Исходный файл разрешений не изменяется; прежние отмены продолжают использовать его. Изменённый файл сам по себе не доказывает согласие.
- `prepare-destination --plan <путь> --sha256 <SHA> --approve` создаёт и проверяет список в точной учётной записи и группе, затем останавливается до переноса задач. Для проверки отмены нового режима используйте отдельно подтверждённую синтетическую задачу; основная привязка проекта пока остаётся прежней.
- `apply --plan <путь> --sha256 <SHA> --approve` переносит только UUID из принятого плана. Исполнитель обязан сообщать `guarded_list_creation: true` и проверять `expected_account_id` до создания. Старый исполнитель закрыто отказывает до первой записи.
- Журнал `ai/reminders-project-lists/<UUID>/` содержит план, снимки, состояния шагов и резерв конфигурации. До внешней записи сохраняется состояние на диск и отметка незавершённой миграции. Обычная, структурная и заметочная сверки блокируют затронутый проект до точного завершения.
- Неизвестный результат создания не повторять. `adopt --plan <путь> --sha256 <SHA> --list-id <точный UUID> --approve` требует отдельного явного принятия пустого списка с точными именем, учётной записью и исходной пустой группой. Поиск по похожему имени не служит доказательством.
- Возобновление допускает только исходное состояние или проверенный результат собственного шага. Сохраняются UUID и все пользовательские поля. Старый родитель остаётся в исходном списке, его окончательный подробный снимок хранится в `retired_parent`.
- Канонические задачи мигратор не изменяет и обычную синхронизацию автоматически не запускает. После завершения предложите отдельный просмотр синхронизации, включая неизвестных детей.
- Проекты с квитанциями отмены запрещены для переноса, кроме завершённых исторических отмен по разделу «Историческая отмена при переходе к списку проекта» ниже. `status --plan <путь> --sha256 <SHA>` показывает фазу без записи приложения.


## Отмена задач отдельного списка и свидетельство восстановления

- Обычная отмена отдельного списка использует протокол 2 и только `ai/reminders-standard-allowlist.json`. Смесь старых родительских связей и отдельных списков в одном плане запрещена. Список должен принадлежать одному активному проекту; UUID, название, учётная запись и группа фиксируются. Цель находится в корне и не имеет детей.
- Четыре команды отдельного исполнителя сохраняются. Старое подтверждение восстановления протокола 1 не разрешает протокол 2. Свидетельство протокола 2 фиксирует исходные испытанные список, группу, учётную запись, сборку ОС и SHA исполняемого файла. Окончательная область его применения определена в разделе «Историческая отмена при переходе к списку проекта» ниже.
- Единственный проверочный цикл требует отдельного явного согласия. Команды координатора `verification-create`, `verification-prepare`, `verification-delete`, `verification-restore-preview`, `verification-restore`, `verification-cleanup`, `verification-close` работают только с одной искусственной корневой записью проекта `content-system`. Каждая запись требует `--approve`; UUID операции задаётся через `--operation`, затем используются точные `--plan` и `--sha256`. Восстановление требует свежий `--restore-token`.
- Создание использует обычную команду приложения и сначала сохраняет намерение. Неизвестный результат создания не повторяется. Проверочный план содержит `purpose=project_list_verification`, точный marker и отдельную временную связь `project_list_verifications`. Реальных Task ID, канонических файлов задач и обычных квитанций задачи в этом цикле нет.
- Исключение допускает только доказанный `destination_ready` конкретного незавершённого переноса с нулём перемещений. Обычная отмена и восстановление этого проекта остаются заблокированы. После двух мягких удалений и одного восстановления тот же UUID должен остаться удалённым. Повторное cleanup запрещено.
- После независимой проверки родитель вызывает `verification-close`: координатор сравнивает конфигурацию и восстанавливает точные исходные байты pending-конфигурации. Затем `verification-witness --approve --independent-review-accepted --expected-journal-sha256 ...` принимает фиксированный файл `ai/reminders-project-list-verification.json`. Сам цикл не включает возможность.
- Только после завершения переноса `verification-pin --approve --expected-config-sha256 ... --expected-witness-sha256 ...` добавляет SHA свидетельства в конфигурацию. До этого возможность обычной отмены протокола 2 остаётся выключенной. После принятия обычное добавление задач и утверждённых имён списков не отменяет свидетельство. Область применения — та же ОС, точный SHA исполнителя и та же учётная запись по окончательному договору ниже. Текущие список, группа, разрешения и зависимости каждого свежего плана проверяются отдельно.
- Завершённая миграция допускает только это отдельное проверенное поле свидетельства сверх своего точного конечного документа. Все незавершённые состояния сохраняют прежнее побайтное сравнение конфигурации. Другие изменения не получают исключение.
- Состояние и повторное исполнение полностью завершённой обычной отмены допускают посторонние поля конфигурации. Целевые связи, квитанции, разрешения, реестр, политика и снимки проверяются заново. Наличие хотя бы одного промежуточного элемента сохраняет полную проверку конфигурации. Старый токен восстановления не становится действительным после изменения конфигурации.
- Структурная сверка исключает отсутствующий UUID из дерева только после штатной проверки завершённой квитанции отмены. Повторное появление этого UUID в активном снимке блокирует сверку. Перенос старого дерева с отменами разрешён только по узкому договору раздела «Историческая отмена при переходе к списку проекта» ниже; остальные случаи запрещены.


## Переименование прежнего контейнера и массовые предложения

- `reminders_project_lists.py bulk-candidates --hub <hub>` только читает активные зарегистрированные связи. Результат разделяет подходящие проекты, препятствия и существующие отдельные списки. Целевое имя берётся из `project_label` либо `Name` реестра. Целевая группа — верхний активный предок по карточке и реестру групп, с точной разрешённой нативной связью. Команда не создаёт группы, планы или файлы.
- Предложение не разрешает запись. Выполняйте переносы последовательно, каждый раз создавая свежий частный план после предыдущего сохранения. Плохие связи и исторические отмены вне узкого договора раздела «Историческая отмена при переходе к списку проекта» ниже остаются препятствиями. Не воссоздавайте отсутствующие UUID и не переносите внепроектные корневые записи.
- При совпадении канонического имени с прежним контейнером сначала переименуйте контейнер в `<имя> — прежний список`. Все такие переименования выполняйте до переносов проектов из этих контейнеров. Уже перенесённые контейнеры, исторические отмены, ссылки `retired_parent` и незавершённые операции не поддерживаются этим действием.
- Оба имени заранее включаются в текущий стандартный файл разрешений отдельными принятыми планами разрешения. Конфигурация должна уже выбирать `ai/reminders-standard-allowlist.json`. Исходный файл разрешений неизменяем. Наличие файла без подтверждённой квитанции недостаточно.
- `rename-preview --hub <hub> --list-id <UUID> --expected-name <старое> --new-name <новое>` сохраняет неизменяемый план с полным снимком контейнера, всеми затронутыми связями, исходной конфигурацией и хешами. `rename-apply --plan <путь> --sha256 <SHA> --approve` требует точного одобрения этого плана. `rename-resume` использует те же параметры; `rename-status` только проверяет состояние.
- До переименования журнал сохраняет намерение на диск, а общая отметка блокирует все затронутые проекты. После полного чтения результата локально меняются только их `list_name`. UUID, группы Хаба, прочие связи и канонические задачи сохраняются. Неизвестный исход допускает продолжение лишь из исходного состояния либо точного ожидаемого результата при собственном сохранённом намерении. Сторонние изменения останавливают операцию.
- `detailed_reminder_snapshot: true` разрешает полный подробный снимок одним процессом на начале, возобновлении и финале. Повреждённый обещанный ответ вызывает отказ без переключения на старый путь. Между границами сохраняется кэш отдельных версий: новые и изменённые строки читаются отдельно, родители с детьми перечитываются независимо от версии. Отсутствие возможности сохраняет прежний путь чтения. Проверки полноты, состава, чужих строк и каждого перемещения остаются обязательными.


### Историческая отмена при переходе к списку проекта

Завершённую отмену прежнего протокола переносить только после проверки исходного неизменённого плана, точной квитанции, канонического блока dropped, удалённого UUID и прежнего родителя. Такой UUID не входит в список активных переносов. После переноса повторно проверить удалённое состояние. Старый task link, план отмены и журнал при миграции не изменять.

Новая привязка содержит точную ссылку и SHA отдельной квитанции `historical_binding_migrations`. Квитанция закрепляет исходный план, выбранный элемент и выбранную квитанцию удаления, утверждённый план миграции, старую и новую структурные области, конечный снимок сохранённого родителя и исполняемую сборку. Общий изменяемый журнал отмены и несвязанные поля задач в исторический SHA не входят. Для межъязыковой проверки вложенные JSON-строки хешируются по исходным UTF-8 байтам и затем сравниваются по смыслу с исходными объектами; сериализаторы Python и Swift не считаются одинаковыми.

Будущее восстановление требует отдельного свежего плана и явного запроса. Сначала прежний проверенный механизм возвращает UUID в прежний список и прежнему родителю. Затем обычный перенос активной записи с текущей версией переводит UUID в корень текущего списка проекта. Только после обоих контрольных чтений восстанавливаются канонический текст и исходная связь. Журнал фиксирует намерение до каждой операции; незавершённое восстановление блокирует синхронизацию. Неизвестный результат разрешается по точным собственным снимкам; автоматическое повторное удаление запрещено. Эти операции не атомарны. Реальное восстановление исторических отмен отдельно не доказано проверкой корневого механизма.

Принятое корневое свидетельство относится к той же версии ОС, точному SHA исполнителя и той же учётной записи. Каждый свежий план всё равно проверяет текущий список, группу, разрешения, роль, исключительное владение, реестр, снимок и версию. Добавление обычных задач и утверждённых имён списков не меняет историческое свидетельство; удаление исходных разрешений, повреждение квитанции или смена сборки закрывают доступ. Нельзя выдавать искусственный журнал за реальное свидетельство.

### Намеренно удалённые внешние задачи

Если человек явно исключил точный набор ненайденных задач, используйте только
`scripts/reminders_external_retirement.py preview/apply/resume/status`.
План закрепляет проект, Task ID, UUID и точное подтверждённое решение человека.
Полные краткие снимки каждого доступного разрешённого списка подтверждают только
«не возвращено в текущей разрешённой области». Ошибка, отказ доступа или неполный
ответ не подтверждают отсутствие. Процесс не восстанавливает и не удаляет задачи
в приложении. Проверенная запись меняет канонический статус на `dropped`, сохраняет
исходную связь и отдельную квитанцию `external_retirement`. Это не нативная отмена
и не разрешение восстановления. Повторное появление UUID останавливает обработку.
Неполный журнал блокирует обычную синхронизацию затронутого проекта.

Для существующего пустого проекта используйте отдельные команды
`reminders_project_lists.py empty-rebind-preview/empty-rebind-apply/empty-rebind-resume`.
Разрешены только прежние связи с проверенными квитанциями внешнего исключения,
без активных задач и истории. Роль `direct` допустима только при единственном
владельце и отсутствии чужих прежних или структурных ссылок на этот список.
Старый родитель отсутствует; точный прежний список
либо отсутствует в доступной области, либо полностью пуст. Совпавшее имя не даёт
права принять другой UUID. Имя проекта и верхняя группа берутся из реестра;
учётная запись — из точной целевой группы. Перед созданием действует отдельный
проверенный план разрешения имени списка. Неизвестный исход создания запрещает
повтор. Старая связь и наблюдение сохраняются как происхождение; вымышленный
`retired_parent` запрещён. Обычные проверки переноса и нативной отмены сохраняются.

Доказательство внешнего исключения хранится отдельно для каждой операции проекта
в `external_retirements_completed[project_id][operation]`. Следующее исключение
другой задачи сохраняет прежние доказательства и неизменённые квитанции.
Проверка квитанции требует доказательство именно её операции и точного предмета.

При согласовании пустой привязки явная отметка `project_list_migrations_pending`
сохраняется после записи итоговой привязки, до контрольного чтения конфигурации
и удалённого списка и сохранения `phase=complete`. Только затем снимается отметка.
Возобновление завершённого журнала с оставшейся отметкой повторяет проверки
и снимает отметку без повторного создания списка. Незавершённый журнал блокирует
проект даже при наличии итоговой контрольной суммы в конфигурации.

## Прямое переназначение существующей задачи

`reminders_task_reassignment.py` переносит только одну явно выбранную человеком существующую future/ready-задачу в уже подготовленный исключительный project_list. Точный UUID, исходная пара проект/Task ID, назначение и решение человека входят в неизменяемый план. Новый ID проходит валидатор назначения; UUID сохраняется. Исполнитель меняет только доказанный компактный маркер и управляемую подпись заметки, сохраняет пользовательский текст, срок и повтор. Он не создаёт, не удаляет и не восстанавливает напоминания. Полная прежняя запись и связь остаются в отдельной квитанции происхождения, а не в истории повторений. Неизвестные состояния, внешние ссылки и выбранная история повторений требуют отдельного решения. Общий замок, журнал до каждой записи и точное сравнение двух канонических проекций и конфигурации блокируют обоих участников до полного подтверждения. Обычная защита от пропавшей задачи остаётся обязательной.


## Подтверждённые повторения и отсутствующая история

В принятом режиме главной копии в «Напоминаниях» запись без служебного кода
связывается с выполненным повторением только по прямому решению пользователя
с точными UUID и Task ID. Команда `reminders_recurrence.py preview --hub <hub>
--target <target.json> --user-intent <intent.json>` сохраняет точный план.
`apply --plan <plan.json> --sha256 <sha>` проверяет свежие версии, принадлежность
списка и неизменность плана, затем записывает только проверенную связь истории.
Она не завершает серию и не изменяет приложение. Решение о конкретном совпадении
не становится разрешением связывать другие записи по названиям.

При исчезновении завершённых исторических UUID обычная входящая сверка
сохраняет прежнюю историю и отдельное свидетельство полного чтения разрешённой
области. Неполное чтение, чужой аккаунт, подмена свидетельства или возвращение UUID
останавливают проверку; отсутствие истории не отменяет действующую серию.
Обычные выполненные записи приложения импортируются отдельно. Название может
остановить неоднозначный импорт повторения, но никогда не доказывает его связь.

## Продолжение переноса списков после правок задач

Если во время переноса списков пользователь изменил задачи, прежний снимок
не разрешает продолжение. Отдельная команда `reminders_structure_restart.py`
готовит свежий план без записи в приложение. Она принимает только доказанный
префикс прежних переносов целых списков. Группы, аккаунты, локальные исходники,
точные шаги и конечный результат должны совпасть
с прежним намерением. Переносы отдельных задач этот путь не поддерживает.
Перенос самого проекта с квитанциями отмены или истории требует отдельного
проверенного восстановления. Квитанции других проектов сохраняют прежнюю привязку.
Новые поля задач сохраняются целиком; база задач не изменяется.
Два свежих полных чтения должны совпасть. Применение по сохранённому плану
и его контрольной сумме повторяет проверку. Старый журнал сохраняется целиком.
Промежуточное состояние блокирует обычную сверку до штатного продолжения
того же плана. Любое третье состояние остаётся ошибкой.
