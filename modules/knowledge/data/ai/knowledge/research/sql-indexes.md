# Индексы SQL: ускорение чтения и стоимость обслуживания

## Statement

Самостоятельный конспект предоставленной статьи с отдельными уточнениями по официальной документации PostgreSQL 18. Статья вводная; её категоричные обобщения нельзя переносить на все системы управления базами данных.

### Основные идеи статьи

- Индекс — отдельная структура для поиска строк. Он может сократить объём чтения по сравнению с просмотром всей таблицы.
- B-tree хранит упорядоченные ключи и подходит для ряда запросов на равенство, диапазоны и сортировку. Фактическая польза зависит от запроса и данных.
- Статья рассматривает уникальные, составные, частичные и покрывающие индексы, а также упоминает специализированные методы. Это разные свойства и способы организации, а не взаимно исключающие категории.
- Порядок колонок составного индекса важен. Начальные колонки часто определяют, насколько узкую часть индекса нужно прочитать.
- План запроса показывает выбор оптимизатора. Наличие индекса не гарантирует его применение; чтение таблицы может быть дешевле для небольшой таблицы или большого числа подходящих строк.
- Индексы занимают место и требуют обслуживания при изменениях данных. Их выбирают под фактическую нагрузку чтения и записи, а не создают на каждой колонке.
- Статья предлагает искать проблемные запросы, проверять план и оценивать пользу индекса. Неиспользуемые индексы требуют анализа; конспект не разрешает их удаление.

### Проверенные уточнения

1. **Составной индекс может работать без условия на первую колонку.** PostgreSQL 18 допускает использование B-tree с условиями на разные подмножества колонок. При подходящих данных оптимизация пропуска начальных значений (skip scan) выполняет повторные поиски по значениям пропущенной начальной колонки. Эффективность зависит от числа этих значений и оценки оптимизатора. Фраза статьи «индекс уже не поможет» слишком категорична. [Документация](https://www.postgresql.org/docs/18/indexes-multicolumn.html).
2. **Функция над полем не запрещает индексацию вообще.** Индекс по самому полю и индекс по выражению различаются. Для запроса по результату функции PostgreSQL позволяет создать соответствующий индекс по выражению. Обобщение статьи об обязательном полном переборе неверно без этой оговорки. [Документация](https://www.postgresql.org/docs/18/indexes-expressional.html).
3. **Поиск с процентом в начале не всегда требует полного чтения таблицы.** Обычный B-tree имеет ограничения, но расширение pg_trgm поддерживает индексный поиск LIKE/ILIKE без фиксированного начала строки. Эффективность зависит от извлекаемых триграмм. [Документация](https://www.postgresql.org/docs/18/pgtrgm.html).
4. **EXPLAIN ANALYZE действительно выполняет запрос.** Это не просто просмотр предполагаемого плана. Документация показывает фактические строки и время, а также отличает условную стоимость плана от миллисекунд выполнения. Примеры из статьи здесь не запускались. [Документация](https://www.postgresql.org/docs/18/using-explain.html).
