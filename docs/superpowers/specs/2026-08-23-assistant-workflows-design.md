# Сценарии AI-ассистента и подтверждения

## Общий принцип

AI-архитектура — единственный источник правды для проектов, задач, подзадач,
ожиданий и сроков. Obsidian и Calendar — представления или внешние цели
записи. Каждый workflow сначала возвращает предложение; он ничего не записывает
сам.

Новый запрос начинает с `metadata-search`. Чтобы прочитать task, project memory
или knowledge, agent показывает ID, путь, цель и границы, затем получает
`confirmed-project` или `confirmed-set`. Ссылка из заметки или встречи — только
подсказка, а не доступ. Каждая запись после чтения требует ещё одного явного
подтверждения пользователя непосредственно перед ней.

## Единый proposal envelope

Любая возможная запись показывается отдельным объектом в разговоре. По
умолчанию он не сохраняется: постоянная очередь предложений не нужна, пока не
доказана её необходимость.

```yaml
proposal_id: P-20260824-001
action: create_task
target_project: hadassah-seo-analytics
target_path: ai/current-task.md
summary: Проверить отчёт подрядчика
due: 2026-08-26
source: meeting-note-id
requires_confirmation: true
```

Обязательные поля — `action`, `target_project`, `target_path`, `summary`,
`due`, `source`, `requires_confirmation`; `proposal_id` добавляется для выбора
части пакета. `due: none` допустим только с явной пометкой «срок не назван».
Перед подтверждением agent показывает также точное изменение файла или
Calendar-события, старое/новое значение и rollback.

Правила решения:

- `approve P-...` разрешает только названное действие, в названном месте и
  только непосредственно сейчас;
- частичное одобрение применяет только перечисленные proposal ID; остальные
  остаются текстом в разговоре;
- отклонение ничего не записывает, не меняет status и не посылает сообщений;
- измененный проект, путь, срок или destination аннулирует старый proposal:
  agent заново маршрутизирует данные, показывает новый diff и ждёт нового
  подтверждения;
- proposal истекает после завершения текущего запроса, изменения исходных
  данных или явного отказа. Старый текст нельзя применить автоматически в
  другой день или сессии;
- один ответ может подтвердить несколько записей, только если в нём перечислены
  все proposal ID, точные пути/Calendar-события и изменения. Это всё равно
  явное подтверждение непосредственно перед каждым перечисленным действием.

## «План дня» и вечернее ревью — 15 минут

### Вход

Пользователь даёт дату и, при необходимости, доступное время/энергию. Agent
делает metadata-search по зарегистрированным проектам, показывает кандидатов и
просит подтвердить именованный набор для чтения текущих task, future tasks,
waiting и paused work. Calendar доступность читается только через будущий
одобренный интеграционный маршрут; создание или изменение события всегда
остаётся proposal.

### Выход «План дня»

Результат имеет ровно следующие разделы:

1. `Сегодня: контекст` — дата, доступное время и подтверждённый scope.
2. `Три главных действия` — три выполнимых результата, а не три проекта.
3. `Остальные действия` — небольшой ранжированный список с проектом и сроком.
4. `Ожидания и follow_up` — что проверить сегодня и у кого ждём ответ.
5. `Риски и сроки` — просрочки, конфликт сроков, отсутствующие данные.
6. `Календарь` — только предложение слотов/событий, без записи.
7. `Нужны решения` — proposal envelope для задач, сроков или Calendar.

Если набор проектов не подтверждён, agent выдаёт только безопасные метаданные и
просит scope; он не угадывает задачи по названиям Kanban-карточек.

### Вечернее ревью: 15 минут

Вход — фактический результат дня, текущий подтверждённый scope и при желании
доступность завтрашнего дня. Выход имеет эти разделы:

1. `Сделано` — только подтверждённые пользователем результаты.
2. `Перенос` — незавершённое с причиной и предложенной датой.
3. `Ожидания` — новые и существующие waiting task/subtask.
4. `Follow-ups` — завтра, позже и уже просроченные проверки.
5. `Завтрашний Calendar` — только proposal слотов или событий.
6. `Три главных действия завтра`.
7. `Подтвердить` — точный пакет изменений либо пустой ответ «нет записей».

Ревью не завершает задачу, не переносит срок и не создаёт Calendar-событие по
самому факту разговора. Любая такая правка оформляется proposal envelope.

## Ревью недели — 30 минут, в воскресенье

Недельное ревью начинается не со списка разрозненных задач, а с archiproject.
Для каждого подтверждённо прочитанного archiproject agent показывает:

1. `Target` и единицу;
2. фактический прогресс из primary project contribution;
3. forecast к сроку с допущениями;
4. вклад каждого проекта без двойного учёта related-связей;
5. waiting, ближайшие follow_up и риски;
6. только затем — drill-down в проект, если метрика, просрочка или blocker
   требует объяснения.

Завершение ревью: три главных результата недели, кандидаты на паузу/возобновление,
предложения review дат и Calendar-блоков, затем proposal envelope. Никакой
проект не получает новый status только потому, что он появился в недельном
списке.

## Быстрый capture и разбор встречи

### Входы

Поддерживаются три одинаково безопасных входа:

- текстовая заметка или краткое сообщение;
- аудиофайл с просьбой сделать расшифровку;
- готовая расшифровка.

Сначала agent возвращает структурированный разбор: участники/контекст, решения,
кандидаты на задачи, возможные project ID, владельцы, сроки, ожидания и
неясности. Audio и transcript, предоставленные пользователем в текущем запросе,
не дают доступа к связанным проектам. Если для сопоставления нужно прочитать
проект или старую knowledge, agent показывает кандидаты из metadata-search и
запрашивает scope.

### Каноническая запись встречи

После подтверждения будущая одна canonical meeting record создаётся в
`Resources/Meetings/<YYYY-MM-DD>-<slug>.md`. Она содержит исходный материал или
ссылку на него, краткое резюме, решения, неопределённости и список
зарегистрированных `project_id`. Это одна общая запись, а не её копии по
проектам. Ссылка на project ID остаётся discovery hint и не предоставляет
доступа.

Для каждого проекта agent создаёт отдельный proposal task в его каноническом
`ai/current-task.md` либо `ai/future-tasks.md`. Задача хранит ссылку на meeting
record, но meeting record не хранит вторую изменяемую копию task. Перед записью
встречи и перед каждой project task пользователь подтверждает точные пути и
diff; можно одобрить встречу, но отклонить все задачи, или наоборот.

Если владелец не назван, поле получает `owner: unknown`, а не имя по догадке.
Если срок не назван или неясен, agent предлагает `due: none` либо несколько
вариантов и вопрос; он не выдумывает дату. Неясное назначение проекта остаётся
в `Inbox` только после отдельного подтверждения соответствующей записи.

## Follow-up и ожидания

`follow_up` существует только внутри waiting task/subtask вместе с
`waiting_for`, `waiting_since` и `next_after_response`. В «Плане дня» он
показывается по дате: сегодня, ближайшие дни или просрочено. Для него agent
может предложить Calendar-slot либо событие, но не создаёт его сам.

Пропущенный follow_up — рекомендация: «проверить ответ» или «предложить новое
сообщение». Он не отправляет автоматическое message, не меняет status, не
переносит срок и не эскалирует без proposal envelope и явного подтверждения.

## Контрольные примеры

- Пользователь одобрил только создание meeting record: задачи остаются
  предложениями и не появляются в проектах.
- Пользователь поменял deadline: старый proposal истёк; agent показывает новый
  diff, а затем ждёт нового подтверждения.
- В одной встрече два project ID: agent создаёт одну canonical meeting record
  и две независимые project-specific task proposals; он не читает третий
  упомянутый проект без scope.
- Waiting subtask просрочена, но у проекта есть активная работа: она попадает в
  follow-up, проект остаётся `Active`.
- Пользователь ничего не одобрил после ревью: итог остаётся в разговоре, а
  architecture, Obsidian и Calendar не меняются.
