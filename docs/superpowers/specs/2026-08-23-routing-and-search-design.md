# Маршрутизация и гибкий поиск

## Статус решения

Это спецификация уже одобренного принципа: межпроектный поиск по безопасным
метаданным может быть гибким, но чтение памяти или knowledge требует явного
подтверждения точного scope. Ссылка служит только подсказкой и никогда не даёт
доступ.

AI architecture остаётся `source of truth` для проектов и задач. Obsidian и
workflow получают только производные представления. Они не создают второй
изменяемый реестр и не записывают через поисковый индекс проектные данные.

## Непересекаемые правила

1. Поиск не равен доступу. Результат поиска, высокий score и точное совпадение
   ID не разрешают чтение проекта.
2. Реестр определяет существование ID, статус и точный путь проекта. Карточка
   даёт только безопасные метаданные. Путь из заметки или ответа пользователя
   не заменяет путь реестра.
3. Полное чтение начинается только после явного подтверждения показанного ID,
   зарегистрированного пути и границ текущего запроса.
4. Разрешение не передаётся по ссылкам и не расширяется транзитивно.
5. Все пути проверяются относительно единственного `allowed roots`. Выход за
   него, подмена пути и `symlink`-переход запрещены.
6. Поисковый и подтверждённые scopes дают только чтение. Каждая отдельная
   запись требует явного подтверждения пользователя непосредственно перед этой
   записью. Запуск write workflow, подтверждение read scope или любое более
   раннее подтверждение не заменяет это разрешение.

## Три read scope

### `metadata-search`

`metadata-search` доступен до подтверждения проекта. Он может искать сразу по
всем зарегистрированным проектам, но только по пяти полям компактного индекса:

- `project_id` — зарегистрированный ID;
- `name` — имя;
- `tags` — список тегов;
- `status` — статус проекта;
- `purpose_brief` — краткая цель из карточки.

Допустимы точное совпадение, поиск по словам, фильтр по status, исправление
простых опечаток и смысловое ранжирование. Точное совпадение `project_id`
всегда выше неточного. Ранжирование — только способ выбрать кандидатов; оно не
меняет права.

Поиск может проверить у любого числа зарегистрированных записей только
компактную проекцию ровно этих пяти полей. До подтверждения router не открывает
и не читает полные карточки кандидатов или любые поля сверх `project_id`,
`name`, `tags`, `status` и `purpose_brief`. После ранжирования он показывает
короткий список из этой же проекции. Он не читает `ai/` проекта, project-local
`knowledge/`, код, историю Git или цель ссылки. Путь берётся из реестра только
для показа кандидата перед подтверждением и не становится поисковым полем.

### `confirmed-project`

`confirmed-project` возникает после явного подтверждения одного точного
`project_id` и его точного зарегистрированного пути для текущего запроса. Он
разрешает:

- читать память `ai/` только этого проекта;
- читать только явно выбранные пути внутри project-local `knowledge/`;
- использовать прочитанное только для подтверждённого запроса.

Выбор `knowledge/` задаётся точным относительным файлом, папкой или явно
названным task-linked набором. Значение `all knowledge` не выводится из самого
факта подтверждения проекта. Код и прочий project content также не получают
глобальное разрешение от этого scope: их чтение остаётся частью отдельно
заданной проектной задачи.

### `confirmed-set`

`confirmed-set` — именованный набор зарегистрированных проектов, одобренный
для одного запроса на сравнение или на его производное агрегированное
представление (например, один снимок общей доски). Представление не является
новым scope: оно использует только данные этого сравнения и только для
показанной цели. Перед чтением agent показывает:

- цель сравнения;
- каждый `project_id` и его точный зарегистрированный путь;
- границы памяти и точные knowledge-пути для каждого проекта;
- при archiproject-обзоре — точные ID и записи из hub-owned
  `ai/archiprojects.md`, необходимые только для primary-вкладов показанного
  набора;
- срок: только текущий явный запрос.

Одно подтверждение разрешает только показанный набор. Добавление ещё одного
ID, расширение knowledge-пути или переход к другой цели требует нового показа
и нового подтверждения. ID в найденной заметке не добавляются автоматически.

## Матрица разрешений

| Scope | Как появляется | Что можно читать | Что нельзя читать | Когда истекает |
| --- | --- | --- | --- | --- |
| `metadata-search` | Новый запрос без project confirmation | Пять полей компактного индекса; зарегистрированный путь только для показа выбранного кандидата | Память, knowledge, код, Git и содержимое целей ссылок | После маршрутизации или завершения запроса |
| `confirmed-project` | Пользователь подтверждает один показанный ID, путь и границы запроса | `ai/` одного проекта и явно выбранный project-local `knowledge/` | Другие проекты, невыбранный knowledge и всё, что добавлено ссылкой | После завершения или отказа от текущего запроса; при новом несвязанном запросе |
| `confirmed-set` | Пользователь подтверждает показанный набор ID, путей, границ и цель сравнения/одного производного представления | Указанные границы каждого проекта набора; при явно показанном archiproject-обзоре — только нужные записи `ai/archiprojects.md` | Любой неуказанный проект, путь, archiproject-запись или новая цель | Сразу после одного запроса на сравнение/представление; при изменении набора или цели |

Ни один scope не разрешает запись. `active-project`, прошлая сессия,
сохранённая заметка и прежний `confirmed-set` не являются постоянным доступом.

## Контракт compact index

Compact index — логический read-only контракт над существующими hub-owned
реестром и карточками. Для него не создаётся новая каноническая база. Реализация
может вычислять представление в памяти или публиковать generated projection,
но такое представление всегда пересобирается из источников и никогда не
редактируется вручную.

Одна запись имеет только этот payload:

```yaml
project_id: example-project
name: Example Project
tags:
  - example
status: active
purpose_brief: Коротко описать назначение проекта.
```

Правила контракта:

- `project_id` и `status` берутся из реестра; путь проекта остаётся отдельным
  routing-атрибутом реестра;
- `name` и `tags` берутся из зарегистрированной записи, `purpose_brief` — из
  её карточки;
- отсутствующее значение отмечается как `unknown`, а не угадывается из имени
  папки, ссылок или содержимого проекта;
- task, subtask, waiting, project memory, личные данные, клиентские данные,
  секреты и фрагменты кода в индекс не входят;
- индекс не хранит независимый task status и не меняет поля, утверждённые в
  `ai/current-task.md` и `ai/future-tasks.md`;
- проект с `status: archived` может находиться поиском, но статус всегда
  показывается и такой результат никогда не открывается автоматически;
- Obsidian использует `project_id` для отображения и ссылок, а workflow перед
  полным чтением заново сверяет ID, status и путь с реестром;
- расхождение или невалидная карточка понижает запись до доступных проверенных
  полей и блокирует полное чтение до исправления регистрации.

Таким образом, Obsidian и workflow могут независимо фильтровать и ранжировать
один и тот же безопасный payload, не становясь новым `source of truth`.

## Ссылки и multi-project notes

Любая note-to-project ссылка — только `discovery hint`. Это относится к
Markdown-ссылке, wiki-link, пути, упоминанию ID и списку related projects.
Ссылка никогда не повышает `metadata-search` до `confirmed-project` или
`confirmed-set`.

Multi-project note хранит только зарегистрированные project IDs и безопасное
описание связи. Когда agent встречает такие IDs, он может показать их как
кандидатов, но обязан запросить подтверждение до чтения проектного content.
Если проект уже входит в действующий точный scope, ссылка может вести внутри
этого scope; право в таком случае даёт прежнее подтверждение, а не ссылка.

Путь из ссылки не используется для обхода. Agent сначала извлекает ID, затем
находит его в реестре, показывает реестровый путь и проверяет границы. Ссылка
без известного ID, ссылка за `allowed roots` или ссылка через `symlink` не
читается.

## Подтверждение и срок действия

Достаточное подтверждение содержит четыре элемента:

1. scope: `confirmed-project` или `confirmed-set`;
2. точные ID и зарегистрированные пути;
3. цель текущего запроса;
4. разрешённую память и точные knowledge-пути либо явное `knowledge: none`.

Подтверждение может быть коротким ответом пользователя после того, как agent
показал все четыре элемента. Нельзя получать разрешение из молчания, похожего
предыдущего запроса, active-project или общего «посмотри связанные проекты».

Scope живёт до ответа по текущему явному запросу и его прямых уточнений. Новый
несвязанный запрос возвращается к `metadata-search` и маршрутизируется снова.
Постоянное global read permission не создаётся. Для нового сравнения старый
набор нужно показать и подтвердить заново.

Если поиск предлагает расширить набор, agent показывает добавляемые IDs и
границы отдельно. При `declined scope expansion` новый проект не читается;
работа продолжается по прежнему подтверждённому scope либо только по
метаданным, если этого достаточно.

## Проверка пути перед полным чтением

Для каждого ID router выполняет проверки в таком порядке:

1. ID существует в реестре и имеет допустимый status.
2. Зарегистрированный путь совпадает с ожидаемым точным путём.
3. Путь находится внутри единственного `allowed roots`.
4. Компоненты пути проверены через `lstat`; project root и выбранные knowledge
   paths не являются `symlink`.
5. Канонический путь после разрешения не выходит из project root и allowed
   root.
6. Пользователь подтвердил именно этот ID, путь и границы запроса.

Ошибка на любом шаге оставляет scope на уровне `metadata-search`, не заменяет
путь похожим и не продолжает чтение частично.

## Failure cases и acceptance examples

Ниже — обязательные prose tests будущей реализации.

### Обычный выбор одного проекта

**Given:** запрос совпал по name и tags с зарегистрированным проектом.
**When:** `metadata-search` возвращает его безопасный payload и agent показывает
точные ID и путь. **Then:** до ответа пользователя проектная память не читается;
после точного подтверждения создаётся `confirmed-project` только для указанной
цели и выбранного knowledge.

### Unknown ID

**Given:** заметка содержит ID, которого нет в реестре. **When:** router
обрабатывает ссылку. **Then:** он сообщает `unknown ID`, не ищет похожую папку,
не следует пути из заметки и не создаёт подтверждённый scope.

### Archived project

**Given:** поиск находит зарегистрированный проект со status `archived`.
**When:** результат показан пользователю. **Then:** metadata видны с явной
меткой `archived`, но память не читается. Для чтения нужно отдельное точное
подтверждение архивного ID, пути и границ текущего запроса.

### Link outside allowed roots

**Given:** Markdown-ссылка указывает на существующий путь вне `allowed roots`.
**When:** agent проверяет её. **Then:** ссылка остаётся discovery hint, путь не
читается и не предлагается как замена зарегистрированному проекту.

### Symlink escape

**Given:** зарегистрированный или knowledge-путь содержит symlink, который
ведёт наружу. **When:** выполняются `lstat` и каноническая проверка. **Then:**
чтение блокируется до безопасного исправления; совпадение ID и confirmation не
отменяют блокировку.

### Personal/work mixed search

**Given:** запрос по tags и purpose находит personal и work проекты. **When:**
выполняется `metadata-search`. **Then:** безопасные записи могут быть показаны
рядом с ID и status без чтения содержимого и без смешивания личных или рабочих
данных. Для сравнения content agent показывает точный `confirmed-set`; только
этот набор и эта цель становятся доступны после подтверждения.

### User declines expanded scope

**Given:** действующий `confirmed-project` и найденная ссылка на второй проект.
**When:** agent предлагает расширение, а пользователь его отклоняет. **Then:**
второй проект не читается, ссылка не даёт доступ, и ответ строится из первого
scope и безопасных metadata с явным указанием ограничения.

### One-request set expiry

**Given:** пользователь подтвердил два проекта для одного сравнения. **When:**
сравнение завершено и начинается несвязанный запрос. **Then:** старый
`confirmed-set` истёк; router снова начинает с `metadata-search` и просит новое
точное подтверждение перед любым полным чтением.
