# Проекция AI-архитектуры в Obsidian

## Решение и границы

AI-архитектура остаётся единственным `source of truth` для проектов, задач,
подзадач, ожиданий и сроков. Obsidian — локальный человеческий интерфейс:
доска, страницы обзора и база знаний. Карточка Kanban, чекбокс и frontmatter в
Obsidian не становятся самостоятельной задачей и не могут менять архитектурную
запись сами по себе.

Любая будущая запись, перенос, удаление, изменение срока, пересборка файла
проекции или Calendar-события возможны только после **явного подтверждения
пользователя непосредственно перед действием**. Ранее начатый workflow,
просмотр доски или старое согласие такого подтверждения не заменяют.

Это проектирование не меняет живой vault и не мигрирует копию vault.

## Механизм проекции

Сравниваются ровно три способа. Оценка: `5` — лучше; для setup cost `5`
означает наименьшую стоимость запуска.

| Способ | Setup cost | Безопасность записи | Безопасность маршрутизации | Offline | Риск дубликатов | Вывод |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Generated Markdown views | 3 | 5 | 5 | 5 | 5 | Чистый основной вариант. Генератор читает канонические файлы в подтверждённом scope и создаёт только заменяемые представления. |
| Obsidian plugin/script, читающий compact indexes | 4 | 4 | 3 | 5 | 4 | Дешёвый fallback для простого списка проектов; плагин требует отдельной проверки разрешений и не читает полные файлы. |
| Vault layout, который напрямую открывает approved folders | 5 | 5 | 2 | 5 | 5 | Полезен для ручной навигации, но сам не делает общую доску и легко создаёт ложное ожидание глобального доступа. |

### Выбранный вариант

**Чистый вариант — generated Markdown views.** Команда «предложить обновление
доски» сначала показывает точный список project ID, исходные файлы и целевой
файл Obsidian, но ничего не читает вне metadata-search. Пользователь
подтверждает этот `confirmed-set` как один запрос на агрегированное
представление; это частный случай разрешённого сравнения и не создаёт нового
или постоянного scope. Только после этого agent читает показанные границы и
создаёт read-only preview в памяти, без записи в vault.

После preview agent показывает отдельный write-diff: создать или заменить
конкретный Markdown-файл и конкретный manifest, с путями и контрольными
хешами. Только второе, явное подтверждение непосредственно перед этими двумя
записями разрешает их выполнить. Представление несёт метку генерации, время,
список ID и пути-источники. Его можно полностью пересобрать; вручную
отредактированные архитектурные данные не сохраняются в нём.

Общая доска может содержать следующие действия только потому, что пользователь
подтвердил конкретный набор проектов для её сборки. Агент не получает права
позже читать всю доску как обход маршрутизации: при новом запросе он снова
начинает с `metadata-search` и открывает проекты только после нового
подтверждения. Снимок на доске предназначен пользователю, а не является
глобальным агентским индексом.

**Дешёвый fallback — plugin/script, читающий compact indexes.** Он показывает
только разрешённые поля metadata-search: ID, имя, теги, status и краткую цель.
До отдельного подтверждения такой plugin не показывает задачи, ожидания,
содержимое карточек или knowledge. Новый плагин и его разрешения требуют
отдельного решения; наличие установленного `obsidian-kanban` этого решения не
заменяет.

Прямое открытие approved folders сохраняется как ручной способ открыть уже
разрешённый проект. Ссылка, папка или wiki-link остаются только discovery hint;
они не повышают scope и не разрешают переход за allowed roots или через
symlink.

## Kanban задач и обзор проектов

Vault хранится локально в `obsidian-vault/` проекта AI-архитектуры и исключён
из Git. В его корне создаются три сгенерированных файла:

- `Tasks-Kanban.md` — Kanban-вид, совместимый с `obsidian-kanban`;
- `Projects-Overview.md` — таблица проектов;
- `AI-Architecture.manifest.json` — общая контрольная запись для обоих видов.

Карточка `Tasks-Kanban.md` равна одной канонической задаче, а не проекту.
Колонки — статусы задач: `Ideas`, `Ready`, `Active`, `Waiting`, `Blocked`,
`Review`, `Paused`, `Done`. На карточке есть название задачи, родительский
проект и подтверждённый срок, если он записан. `idea` показывает будущую
задачу в `Ideas`; `promoted`, `done` и `dropped` не создают открытых карточек.

`Projects-Overview.md` содержит одну строку на проект: название, статус
проекта, текущая задача, количество ready- и waiting-задач и ближайший срок.
Это таблица, потому что статусы проекта и задачи — разные сущности; проект не
переносят между колонками статусов задач.

### Ручное изменение видов

Пользователь может править карточку или таблицу, но эта правка — **сигнал
предложения**, не синхронизация. При следующей команде агент сравнивает
изменённый snapshot с manifest генерации в уже подтверждённом scope и
показывает понятный diff: какой канонический файл, поле и значение предлагается
изменить. Он не записывает задачу, срок, статус, заметку или ссылку, пока
пользователь отдельно не подтвердит именно этот diff. После записи в
архитектуру agent отдельно показывает новый diff обоих видов и manifest и получает
подтверждение непосредственно перед их пересборкой. Неподтверждённая ручная
правка помечается `proposal pending` и не влияет на источник истины.

Такой режим не создаёт второго writable task store: единственные канонические
изменения происходят в `ai/current-task.md`, `ai/future-tasks.md`, карточке
проекта или будущей записи archiproject, описанных в модели работы.

## Организация знаний

Предлагаемая структура — PARA с лёгким Zettelkasten, без лишней сущности
«заметка»:

```text
Obsidian
├── AI-архитектура/Projects/       # generated views и ссылки на проекты
├── Areas/                         # постоянные сферы ответственности
├── Resources/
│   └── Meetings/                  # общие материалы и канонические встречи
├── Inbox/                         # только неясное, отложенное, неразобранное
└── Archives/                      # завершённое или неактуальное по решению
```

`Areas` содержит устойчивые личные и рабочие сферы, а не ограниченные цели.
`Resources` содержит переиспользуемые материалы: рецепты, цитаты, статьи,
методы и источники. Лёгкий Zettelkasten означает: у ценной мысли есть своё
короткое название, источник/контекст при наличии и осмысленные wiki-links; не
вводятся обязательные сложные ID и граф ради графа. `Inbox` — запасной буфер:
при ясном маршруте материал сразу предлагается в нужное место.

Знание, нужное одному проекту для его работы, остаётся project-local в его
явно выбранной `knowledge/` области. Общий материал, полезный нескольким
проектам или не привязанный к одному, хранится один раз в общей базе. Например,
одна запись встречи лежит в `Resources/Meetings`; она перечисляет безопасные
project ID и ссылки. Каждый проект хранит только свою task и ссылку на запись
встречи. Ссылка не даёт агенту право читать проект или запись: чтение каждой
стороны всё равно требует подходящего scope.

## Карта миграции без записи

Ниже — классификация для следующего, отдельно подтверждённого этапа. Она
основана на структуре и агрегатах копии vault, а не на телах личных заметок.

| Класс | Что попадает | Будущее действие только после подтверждения |
| --- | --- | --- |
| `keep` | Markdown-заметки, текущие папки знаний, медиа, Canvas и работающие привычные представления | Ничего не переносить; сначала показать роль и целевой путь. |
| `add metadata` | Материалы с однозначной областью, ресурсом или project ID после content-aware review | Предложить минимальные поля типа, связей и даты; не переписывать тело. |
| `review manually` | 3 792 checkbox-строки, 632 wiki-link occurrences, 457 основных заметок, датированные итоги, медиа и Canvas | Разбирать малыми подтверждёнными пакетами; checkbox не считать task без проверки. |
| `archive candidate` | 95 файлов уже в archive, устаревшие итоги и `.trash` | Отдельно показать список; `.trash` не равен Archives и ничего не удаляется автоматически. |
| `duplicate/conflict candidate` | Возможное пересечение старых Kanban с архитектурными задачами, sync-conflict конфигурации, повторные или битые links | Сначала сравнить поля и владельца; затем предложить слияние, пометку или сохранение обеих версий. |

Порядок будущей миграции: (1) сделать резервную копию и список файлов, (2)
включить только новую пустую структуру и один generated view, (3) проверить
его на выбранных проектах, (4) разбирать знания малыми наборами, (5) только
после этого рассматривать старые Kanban. Старые Kanban и checkbox не
автоконвертируются в задачи.

## Проверяемость и rollback

Перед будущей сборкой генератор проверяет project ID, статус, allowed roots,
отсутствие symlink escape, подтверждённый scope и целевой путь. В manifest
фиксируются версия формата, timestamp, ID источников и контрольные хеши;
полные task/knowledge данные в глобальный индекс не добавляются.

Rollback проекции — удалить или восстановить только generated Markdown и его
manifest из Git/backup. Он не меняет AI-архитектуру, исходные заметки,
старые Kanban или Calendar. Rollback одобренной канонической записи выполняется
отдельным Git revert её точного коммита и повторной валидацией архитектуры.
При ошибке или неясной классификации агент прекращает запись, показывает diff
и предлагает `Inbox` либо ручной review.
