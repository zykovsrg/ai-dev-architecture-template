# Безопасная интеграция самоаудита сессий

## Решение

AI-архитектура может раз в несколько дней **предложить** самоаудит, но не
начинает его сама. Предложение не даёт права читать чаты, получать транскрипты,
искать историю или создавать задачу. Оно сообщает цель: проверить работу
архитектуры по свежим сессиям, а не оценивать содержательную работу пользователя.

Перед чтением agent показывает список кандидатов только из безопасных
метаданных: session ID, дата, размер/длина при наличии и связанный project ID.
Пользователь сначала может попросить точное число кандидатов, но **каждый
читаемый transcript требует последующего подтверждения точных session ID**,
например: «проверь эти три ID». Scope действует лишь на этот audit-запрос;
«последние чаты» или «проверь три» без перечня не является подтверждением
чтения.

## Пилот draft-runbook

Источник методики — `hub-session-audit/knowledge/runbooks/session-audit-procedure.md`.
На 2026-08-24 он имеет статус `draft`; журнал показывает `0 из 30` проверенных
сессий. Поэтому первый audit — не регулярная автоматизация, а пилот:

1. Пользователь сам выбирает и подтверждает **three small**, recent,
   non-sensitive sessions. Маленькая — сессия, которую можно разобрать одним
   ограниченным чтением без разбиения; агент не определяет «несенситивность» по
   догадке.
2. Agent читает только три названных транскрипта и применяет все **eight**
   текущих пункта runbook: идентификация, routing, заголовок работы, skills,
   память, трения, незакрытые хвосты и обход границ.
3. На каждый пункт он даёт либо минимальное доказательство, либо `не найдено`.
   Доказательство — session ID, короткий безопасный фрагмент или имя workflow;
   никаких выводов без evidence.
4. После трёх сессий agent отдельно оценивает полезность каждого из восьми
   пунктов: `полезен`, `слишком шумный`, `не дал evidence`. Он предлагает
   сократить runbook только как отдельную architecture change candidate.

Пилот не меняет files audited sessions, чужие проекты, routing, skills или
архитектуру. Создание даже минимального журнала пилота требует отдельного
proposal и явного подтверждения записи.

## Разрешённые результаты

У каждого результата ровно один из трёх статусов:

| Результат | Когда допустим | Действие |
| --- | --- | --- |
| `no systemic issue` | По восьми пунктам нет повторяемого нарушения, есть только разовое безопасно объяснённое отклонение **или evidence недостаточны**. Причина `insufficient evidence` — пояснение, не четвёртый результат. | Ничего не записывать и не предлагать менять. |
| `candidate future task` | Одна и та же ограниченная проблема подтверждена evidence минимум в двух независимых подтверждённых сессиях. | Показать proposal для нужного `ai/future-tasks.md`; запись только после подтверждения. |
| `architecture change candidate` | Одна и та же системная проблема подтверждена минимум в двух независимых сессиях, либо одна сессия содержит evidence нарушения security boundary или неразрешённой protected write. | Показать evidence и точные затрагиваемые файлы; переходить к изменению только после отдельного `architecture-update` confirmation. |

Ни один результат не возникает из впечатления или одного недоказанного эпизода.
Даже `candidate future task` не создаёт backlog-запись автоматически. Если
пилот не даёт достаточных evidence, итог остаётся `no systemic issue` с
причиной `insufficient evidence`, без предложения изменить архитектуру.

## Приватность, границы и retention

- Нельзя переносить в summary или журнал secret, token, ключ, raw environment
  value, личные данные, patient information или client-confidential text — даже
  как цитату. Вместо значения остаётся `<опущено>`.
- Не делать content-аудит рабочих задач, диагнозов, клиентов или личных
  решений. Scope runbook — соблюдение процедур хаба.
- Для duplicate prevention достаточно минимальной записи: session ID, дата
  аудита, версия runbook, восемь кодов результатов и ссылки на безопасные
  evidence-locations. Полный transcript, длинные цитаты и копия чата не
  сохраняются.
- Если для доказательства нужна личная или клиентская деталь, agent описывает
  только тип нарушения и расположение без значения. Если и это небезопасно,
  он фиксирует `evidence withheld` и не создаёт proposal из такого материала.
- Любое чтение чата происходит только по показанному набору; новый chat,
  ссылка на другой project или продолжение на другой день требуют нового
  подтверждения.

## Поведение предложения

Не чаще, чем раз в несколько дней, assistant может написать: «Есть предложение
проверить 3 недавние сессии по методике хаба. Показать список метаданных?»
Пользователь может отказаться, отложить или выбрать другой набор. Отказ не
меняет schedule, status, future tasks или историю.

После согласия на список agent показывает только метаданные и спрашивает ещё
раз: «Подтверждаете чтение session IDs … для пилота?» Лишь после точного ответа
со всеми ID он читает транскрипты. По завершении agent выводит краткий evidence-backed
отчёт и только затем, при необходимости, proposal envelope из workflow design.

## Контрольные примеры

- Пользователь подтвердил «проверь три недавних» без ID: agent показывает
  кандидаты, но не открывает чат.
- Пользователь подтвердил два ID вместо трёх: это допустимый маленький scope,
  но пилот не объявляется завершённым до третьей отдельно подтверждённой
  сессии.
- В чате найден реальный секрет: он не цитируется, не копируется и не создаёт
  задачу; безопасный audit-result отмечает `evidence withheld`.
- Три сессии показывают одну и ту же пропущенную запись памяти: agent формирует
  candidate future task, но не добавляет её в backlog без подтверждения.
- В evidence видно изменение protected rule без нужного mode: это architecture
  change candidate; исправление не начинается без `architecture-update`.
