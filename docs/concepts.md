# Concepts

Simple explanations of the terms used in this architecture.

## Diff

A diff is a list of changes in the code.

It shows:

- which lines were added;
- which lines were removed;
- which lines were changed;
- which files this happened in.

Example:

```diff
- Button: Save
+ Button: Save task
```

The command to view changes not yet staged for a commit:

```bash
git diff
```

The command to view changes already staged for a commit:

```bash
git diff --staged
```

## Personal AI Hub

Personal AI Hub is the only supported architecture. Shared routing, security
rules, workflows, installation, and updates live in the Hub (`_ai-hub`);
`modules/` is the only distributable architecture source in this repository.

Each project remains an independent Git repository at
`_ai-hub/projects/<project-id>` with its own memory and optional `knowledge/`.

A new Hub chat shows the registered project and exact path, then waits for
confirmation before reading that project's code or memory. Installing or
updating the Hub does not scan, convert, clean up, or move projects.

The former standalone/project-local architecture is retired. Existing folders
move to the Hub only through `hub-project-migrate`: the user separately
confirms a temporary source, reviews an exact preview, and confirms each move
or the displayed batch. Then come separate gates: move → registration
confirmation → registry validation → optional cleanup confirmation. Cleanup is
never automatic and removes only confirmed obsolete shared standalone rules;
project memory, Git metadata, and knowledge stay.

## Modules

The Hub is built from modules in `modules/<id>/`. Each module has a passport,
`module.md`, with these fields:

- `Required` — `yes` for core, projects, tasks: they are always installed.
- `Switchable` — `yes` for knowledge, goals, learning, calendar, planning,
  obsidian: they can be switched off and on (see `docs/update.md`).
- `Depends` — modules that must be installed too. planning depends on
  calendar, so calendar cannot be removed while planning stays.
- `Uses if present` — modules used only when installed. planning uses goals
  and learning; learning uses planning.
- `Rules` — the module's rules file in the Hub.
- `Installs` — `source -> Hub target` lines. The release manifest is built
  from these lines.
- `Repository only` — files that stay in this repository and are never
  installed (tests, the calendar server source, installer scripts).
- `Subscribes` — events the module listens to.

The `release` module holds the installer, updater, and checks; nothing of it is
installed into a Hub.

What an installed Hub gets:

- core rules only in `ai/architecture.md`;
- each other module's rules in `ai/rules/<id>.md`, read only when that module's
  skill or subscription runs;
- `ai/modules.md`, generated by the installer: installed modules, their skills,
  and each event's subscribers. Agents look up optional skills here by role
  (for example, "the planning skill listed in `ai/modules.md`"). A module that
  is not listed is not installed and is never called.

### Events

Modules do not call optional modules directly. A workflow fires an event: it
reads `ai/modules.md` and runs every subscriber listed for that event. With no
subscribers, nothing happens.

| Event | Fired by | Subscribers |
| --- | --- | --- |
| `after-task-write` | `hub-task-intake`, `hub-task-switch`, `hub-task-finish`, `hub-info-update`, after a confirmed task-file write | obsidian (refresh the board) |
| `before-task-confirmation` | `hub-task-intake`, `hub-task-switch`, `hub-task-finish`, before asking to confirm a task write | planning (adds the calendar change to the same confirmation screen) |
| `after-calendar-change` | `hub-calendar`, after a successful calendar change | planning (refreshes the calendar snapshot) |
| `before-task-close` | `hub-task-finish`, after the Done criteria pass and before task memory is cleared | learning (session review), knowledge (may offer a knowledge review) |
| `after-project-create` | `hub-project-create`, after the confirmed scaffold is written | knowledge (creates the empty `knowledge/` scaffold) |

### Boundary check

`scripts/check-module-boundaries.py` checks that each module's files name only
allowed modules: itself, core, projects, tasks, and its `Depends` and
`Uses if present` modules. Anything else must go through an event or
`ai/modules.md`. `architecture-test.sh` runs it with `--strict`, so any
violation fails the tests.

## Work modes

The mode tells what the agent may do right now.

- `Mode: routing` — before a project is confirmed: pick the project and show
  its exact path; read no project code or memory.
- `Mode: review` — check and propose; do not write.
- `Mode: implementation` — perform only the approved writes.

## Architecture update

An architecture update changes the Hub rules, not a project's application.
Before applying it, the agent shows the changed Hub rules, the affected files,
and the token impact, then waits for explicit approval.

## Rule precedence

When rules conflict, the agent applies them in this order (from
`ai/architecture.md`):

1. Direct user instructions and platform safety rules.
2. Hub non-overridable rules: explicit confirmation, allowed roots, secrets,
   and memory isolation.
3. Other Hub architecture, entry, and shared workflow rules.
4. The confirmed project's own instructions, current task, and one matching
   reference or skill.
5. Other relevant project references.

A project can never widen the Hub boundary. When in doubt, the safer boundary
wins.

## Minimalism

Minimalism reduces the burden of understanding, maintaining, and managing a
project. It does not remove safety measures or functionality needed for
correctness, legal compliance, or the user's confirmed goal.

## Project invariants

Project invariants are project rules that must not be broken — the
"load-bearing walls" of the project.

Example:

```text
Microtask must belong to a Week Task.
```

Store them in the project's `ai/project-context.md` under `## Invariants`.

## Skills

Skills are reusable procedures for specific tasks. All Hub skills start with
`hub-` and live in `modules/<id>/skills/`; the Hub installs them into
`ai/skills/`. Examples:

- `hub-task-intake` records a new task in the project's current memory.
- `hub-task-finish` safely closes a task.
- `hub-project-router` picks the project and asks for confirmation.

Skills are loaded only when needed. The full list for an installed Hub is in
`ai/modules.md`.

## Environment check

`hub-environment-check` runs after the project is confirmed. It reads the
project's `ai/current-task.md` (and `ai/paused-tasks.md` only when needed),
reports whether task memory is available, the task's status and stage, and
which workflow comes next: `hub-task-intake`, `hub-task-switch`, or
`hub-task-finish`. It changes nothing.

## Task switching

Before a working task, the agent uses `hub-task-intake`. It reads
`ai/current-task.md`:

- empty → records the new task with its goal, scope, Done criteria, and a
  unique `Task ID:`;
- unfinished → compares the request with the recorded Done criteria; it
  continues only when the request fits, otherwise it hands over to
  `hub-task-switch`;
- an idea for later stays out of the current task until the user approves
  saving it separately.

`hub-task-switch` shows the current goal, the requested replacement, and the
exact files that would change. It pauses the current task, writes the
replacement, or promotes a future task only after a separate explicit
confirmation. A paused task moves to `ai/paused-tasks.md` and keeps its
`Task ID:`. `hub-task-switch` does not close tasks; closing is for
`hub-task-finish`.

## Task finish

`hub-task-finish`:

1. Checks the recorded Done criteria and runs the deterministic task-record
   checks. Nothing is written during the check; a failure leaves the task open.
2. Fires `before-task-close` (for example, the learning module's session
   review). A subscriber failure leaves the task open.
3. Writes the changelog entry, any durable decision, confirmed future tasks,
   and clears `ai/current-task.md`. The close request itself approves this
   write; a separate confirmation is needed only when a subscriber adds items
   to the screen.
4. Saves the result in the project's Git repository and reports the commit and
   whether it was pushed or stayed local.
5. Fires `after-task-write`.

It never touches another project's memory.

## Obsidian task sync (obsidian module)

`ai/current-task.md`, `ai/future-tasks.md`, and `ai/paused-tasks.md` are the
only canonical task records. The Obsidian Kanban is a generated view in the
central vault `<hub>/projects/ai-dev-architecture/obsidian-vault`. The rules are
in `modules/obsidian/rules.md` (`ai/rules/obsidian.md` in a Hub).

After an approved task write, the `after-task-write` event rebuilds the view
with `--write --refresh-from-architecture`. This direction is trusted only from
`ai/` records to the board and still validates the manifest. A manual Obsidian
edit makes the refresh stop with a pending proposal; it never overwrites it.

The reverse direction is a confirmed proposal for one project: scan the board,
check the status, then apply only the shown hash. `--project-id` is required
for `scan` and `apply`.

```bash
bash scripts/obsidian-task-sync.sh scan --project-id <id> --hub /path/to/_ai-hub --scope /path/to/scope.txt --vault /path/to/_ai-hub/projects/ai-dev-architecture/obsidian-vault
bash scripts/obsidian-task-sync.sh status --vault /path/to/_ai-hub/projects/ai-dev-architecture/obsidian-vault
bash scripts/obsidian-task-sync.sh apply --project-id <id> --hub /path/to/_ai-hub --scope /path/to/scope.txt --vault /path/to/_ai-hub/projects/ai-dev-architecture/obsidian-vault --confirm-proposal <sha256>
```

A board edit becomes a proposal only when the synchronizer can express it as an
exact canonical change. It supports renaming a card, changing or removing its
explicit due date, moving a future task between `Ideas`, `Ready`, `Blocked`, and
`Active`, moving the current task between `Active`, `Blocked`, and `Review`, and
creating an unchecked card that names a registered project. Everything else is a
blocked proposal: pausing needs `hub-task-switch`, finishing needs
`hub-task-finish`, a paused card cannot change at all, and a ticked checkbox or
an extra card field blocks the whole board rather than being reverted in
silence by the next refresh.

Promoting a future task into `Active` replaces the project's current task. The
replaced task is written to `ai/paused-tasks.md` with its whole recorded body
kept verbatim as an indented block. The new current task starts from the
promoted title alone; fill in the rest through the normal task workflow.

The optional local watcher only runs `scan`; it never applies a proposal. Its
installer is repository-only; run it from this repository. Installation and
removal are separate actions, each with its own confirmation flag:

```bash
bash modules/obsidian/scripts/install-obsidian-task-sync.sh --hub /path/to/_ai-hub --scope /path/to/scope.txt --vault /path/to/_ai-hub/projects/ai-dev-architecture/obsidian-vault --preview
bash modules/obsidian/scripts/install-obsidian-task-sync.sh --hub /path/to/_ai-hub --scope /path/to/scope.txt --vault /path/to/_ai-hub/projects/ai-dev-architecture/obsidian-vault --install --confirm-launchd-install
bash modules/obsidian/scripts/install-obsidian-task-sync.sh --hub /path/to/_ai-hub --scope /path/to/scope.txt --vault /path/to/_ai-hub/projects/ai-dev-architecture/obsidian-vault --status
bash modules/obsidian/scripts/install-obsidian-task-sync.sh --hub /path/to/_ai-hub --scope /path/to/scope.txt --vault /path/to/_ai-hub/projects/ai-dev-architecture/obsidian-vault --uninstall --confirm-launchd-uninstall
```

`.ai-architecture-sync/` inside the vault holds only local proposals, locks,
and watcher logs; Git ignores it.

## Optional project knowledge (knowledge module)

`knowledge/` is an optional local reference layer. It differs from
`ai/project-context.md`: context holds the current project facts that guide
work; knowledge holds deliberately captured research, decisions, risks, and
runbooks. The rules are in `modules/knowledge/rules.md`.

- A new project gets the empty `knowledge/` scaffold through the
  `after-project-create` event, as part of the same confirmed creation.
- An existing project gets it only through `hub-knowledge-enable`, after a
  separate confirmation. A Hub update never creates `knowledge/` and never
  changes records.
- `hub-knowledge-capture` proposes an exact category and path;
  `hub-knowledge-review` examines only an explicitly selected record or set.
  Neither writes until the user confirms the exact change.
- Records have one of four types (`research`, `decision`, `risk`, `runbook`),
  each in its matching folder, and one of five statuses: `draft`, `verified`, `needs-review`, `stale`,
  `superseded`. Stale and superseded records stay in place and link to their
  replacements.
- Records must contain no secrets, personal data, or client data.
- At task close, the `before-task-close` event may offer a focused knowledge
  review; the offer does not authorize reading or changing knowledge.

Legacy standalone knowledge migration is out of scope.
